# Open Source Growth Plan

A cadence for building a real user base, not just shipping code. This is a plan for
*after* the [Launch Readiness Review](LAUNCH_READINESS.md) passes and the project has
its first public announcement - premature outreach to an unfinished repo burns the
one first impression most people give a new project.

## Weekly

- Ship one meaningful improvement (a real feature or fix, not busywork commits).
- Triage new issues within a few days; close stale ones with an explanation rather
  than letting them rot silently.
- Respond to discussions and PR comments promptly - an unanswered question is the
  single biggest reason a first-time contributor doesn't come back.

## Every release

- Publish release notes with screenshots or a short clip of the feature in action -
  a changelog line rarely conveys what actually changed.
- Record a short demo video for anything user-facing.
- Share a benchmark update if performance-relevant work shipped (see
  [PERFORMANCE.md](PERFORMANCE.md)).

## Monthly

- Publish a technical blog post - architecture decisions, a hard bug post-mortem, or
  a "how we built X" walkthrough. Technical credibility is what makes this kind of
  infrastructure project trustworthy, not marketing copy.
- Host a community Q&A or async discussion thread.
- Review [ROADMAP.md](ROADMAP.md) publicly and adjust it based on what users have
  actually asked for, not just what was originally planned.

## The one rule that matters more than this cadence

Don't chase big new features before there are real users to ask for them. Once
people are actually running Setu Gateway, they'll say which capabilities matter -
let that feedback shape the roadmap after v0.1.0-alpha instead of anticipating every
future need speculatively. A clear vision plus real user feedback beats a long
feature list every time.
